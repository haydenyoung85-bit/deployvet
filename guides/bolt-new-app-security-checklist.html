Bolt.new app security checklist

Before you launch a Bolt.new app, check four things: no secret keys in the frontend, database rules that block strangers, no admin pages open without login, and basic security headers. Bolt writes code fast, but it builds what you ask for. It may not add the safety parts you did not ask for.

Step-by-step checklist

  1. Find where your app keeps keys. Anything starting with VITE_ or used in browser code ends up public.
  2. Move secret keys (Stripe secret, OpenAI, service_role) to a server function or edge function.
  3. If you use Supabase, turn on RLS for every table and check each policy.
  4. If you use another database, make sure the browser never talks to it with admin rights.
  5. Log out and try every admin and API URL. They should return an error, not data.
  6. Check that forms check input on the server, not only in the browser.
  7. Add security headers like Content-Security-Policy and Strict-Transport-Security on your host.
  8. Rotate any key that was ever pushed to a public repo or shown in the browser.

FAQ

Are my .env values in Bolt private?

Only if they stay on the server. Values used in browser code are built into your JS files, where anyone can read them.

What should I do if a secret key leaked?

Make a new key in that service, delete the old one, and move the new one to the server.

Do I need security headers?

They are not a fix for bad data rules, but they block some common attacks. Most hosts let you add them in a config file.
