Supabase RLS check for AI-built apps

To check Supabase RLS, make sure every table in the public schema has RLS turned on, then read each policy to see who it lets in. A table with RLS off can be read by anyone who has your public anon key, and that key is in your site's JS. AI tools often make tables quickly, so it is easy to miss one.

Step-by-step checklist

  1. In the Supabase dashboard, open Table Editor. Any table marked as RLS disabled needs a fix.
  2. Or run this in the SQL editor: select tablename, rowsecurity from pg_tables where schemaname = 'public';
  3. Turn RLS on where it is off: alter table my_table enable row level security;
  4. Read every policy. Watch for using (true) or policies for the anon role on private data.
  5. For user data, limit rows to the owner, for example using (auth.uid() = user_id).
  6. Check insert and update policies too, with with check, so users cannot write rows as someone else.
  7. Test with two accounts. One should not see the other's rows.
  8. Check views and functions. Views and security definer functions can skip RLS if you are not careful.

Supabase also has a Security Advisor in the dashboard. It flags tables without RLS. Run it after each big change.

FAQ

What happens if RLS is off?

Anyone with your anon key can use the Supabase API to read, and maybe change, that table.

Is RLS on enough?

No. RLS on with no policies blocks everyone. RLS on with a loose policy can still let everyone in. The policies matter.

Does the service_role key follow RLS?

No. It skips RLS. Keep it on the server only.
