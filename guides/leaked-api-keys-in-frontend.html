Leaked API keys in your frontend

If a secret API key is in your frontend code, anyone can copy it. Open your site, view the JS files, and search for key patterns. If you find a secret key, make a new one, delete the old one, and move the call to a server. Hiding or scrambling the key in the browser does not make it safe.

Step-by-step checklist

  1. Know the difference. Some keys are meant to be public, like a Stripe publishable key (pk_) or the Supabase anon key. Secret keys are not.
  2. Open your live site. In DevTools, go to Sources and search all files for words like sk_, secret, service_role and api_key.
  3. Check your env files. In Vite, any VITE_ value goes to the browser. In Next.js, any NEXT_PUBLIC_ value does.
  4. Search your repo and its history. A key removed in a later commit is still in old commits.
  5. For each leaked secret, rotate it: make a new key and revoke the old one in that service.
  6. Move the call that needs the key into a server route or edge function.
  7. Set spend limits or usage alerts on paid APIs like AI model providers.

FAQ

Is the Supabase anon key a leaked key?

No. It is built to be public. Your safety comes from RLS.

Can I hide a key with base64 or a minifier?

No. Anyone can undo that in seconds. If the browser can use the key, a person can too.

I deleted the key from my code. Am I safe?

Not yet. It may still be in git history or in cached files. Rotate the key.
